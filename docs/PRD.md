## 原始需求复述

> "我想做一款云顶之弈的自动记录牌库各个弈子所剩余个数的工具。"

经主理人与用户确认的三个关键决策：

1. **应用形态**：Windows 桌面悬浮窗 —— Electron 应用，透明置顶窗口贴在游戏画面上方，后台定时截屏自动更新剩余牌数，边玩边看。
2. **录入方式**：混合模式 —— OCR 自动识别棋盘 / 备战区 / 商店中的弈子，识别不准时用户可手动点一下校正（兼顾省事与准确）。
3. **统计范围**：全场 8 家轮询扫描 —— 自动扫描所有对手棋盘 + 备战区，最准确地推算牌库消耗。这是该工具的核心价值。

## 1. 产品目标

### 1.1 一句话价值主张

**在不碰游戏进程的前提下，把"这一局还剩几张牌"从玄学变成屏幕右上角的实时数字，让你在按下刷新键之前就知道该追还是该转。**

### 1.2 三条产品目标

| # | 目标 | 说明 | 衡量方式 |
| --- | --- | --- | --- |
| G1 | **决策前置** | 在准备阶段的 30 秒内，给出"某张牌还剩几张"的即时答案，替代玩家心算与粗略扫场 | 从"想查某张牌剩余"到"看到数字"≤ 3 秒；单局需手动操作次数 ≤ 3 次 |
| G2 | **覆盖全场** | 把统计范围从"自己的牌"扩展到"全场 8 家的牌"，这是牌库推算准确性的决定性因素 | 典型对局中巡查覆盖率 ≥ 6/8 家；剩余数与真实值偏差 ≤ 2 张（1–3 费）/ ≤ 1 张（4–5 费） |
| G3 | **绝对合规** | 只做"屏幕像素读取 + 识别 + 计数"，不读写进程内存、不注入、不模拟输入、不改文件与网络包，让用户能放心长期开着 | 通过第 8 章全部合规红线项的自检清单；无任何第三方反作弊告警反馈 |

## 2. 用户画像与核心场景

### 2.1 用户画像

| 维度 | 描述 |
| --- | --- |
| 身份 | 云顶之弈国服玩家，Windows PC，段位钻石 ~ 大师，日均 3–8 局 |
| 痛点 | ① 追 3 星时不知道被"卡"了几张，常在牌池已空时硬 D 血崩；② 巡查 7 家靠肉眼记，记不住也记不准；③ 现有工具（MetaTFT / 网页查询）只有"概率表"，没有"本局实时剩余" |
| 现有替代 | 心算、笔纸、切屏查概率表、观战复盘 |
| 关键诉求 | 边玩边看、不打断操作、数字可信、不会被封号 |

### 2.2 典型对局使用流程

```
【开局 1-1 ~ 2-1】
  启动工具 → 悬浮窗吸附在屏幕右侧 → 自动识别当前赛季(S18)并加载卡池基线
  → 识别自己的棋盘/备战席 → 列表初始化，所有弈子显示"剩 30/30"等初始值
  → 用户把想追的 1-2 张卡"钉"到顶部关注区

【2-1 ~ 3-2 刷新商店阶段】
  每次手动刷新/D 牌 → 工具在准备阶段每 1.5s 截屏一次 → 自己的持有数实时更新
  → 关注区"维迦 剩 22/30"绿色，继续追

【3-2 ~ 4-2 巡查对手阶段】★核心价值场景
  用户点击对手头像/Tab 切换巡查视角（工具不模拟输入，被动接收画面）
  → 工具自动识别"当前在看第几家"（计分板高亮 + 棋盘特征）并累加到该家台账
  → 状态条从"巡查 1/8"走到"巡查 7/8"
  → 发现对手B 有 2★ 阿狸 → 阿狸剩余数从 6 掉到 3，关注区变黄

【4-2 决策追 3 星 / 转阵容】★决策时刻
  阿狸 4费：池 10，已知消耗 9 → "剩 1"，还差 5 张到 3★ → 红色告警
  → 用户放弃追 3 星，改为上 9 找 5 费或转 uncontested 阵容
  维迦 1费：池 30，已知消耗 11 → "剩 19"，还差 4 张 → 绿色，继续 D

【战斗/选秀阶段】
  工具自动降频或暂停（画面无完整棋盘，识别无意义），状态条显示"选秀中"
  → 战斗结束回到准备阶段自动恢复高频扫描

【对局结束】
  一键重置台账，开始下一局（可选：本地保存本局记录供复盘）
```

| US-8 | 作为一名**正在打团的玩家**，我希望工具在战斗/选秀阶段自动降频或暂停扫描，以便它不白占 CPU，也不给我弹出一堆无意义的错误识别结果。 |

## 4. 需求池

优先级：**P0 = 必须有（没有就不成立）**，P1 = 应该有，P2 = 锦上添花。

### P0 — Must have

| 编号 | 需求描述 | 验收标准 |
| --- | --- | --- |
| RQ-01 | **透明置顶悬浮窗**：Electron 无边框窗口，始终置顶（Always on Top），支持拖拽移动、边缘吸附、缩放（80%~150%）、不透明度调节（40%~100%）、点击穿透开关 | ① 窗口在 TFT 全屏/无边框窗口模式下稳定置顶不闪烁；② 拖动后位置持久化到下次启动；③ 开启点击穿透后鼠标可穿透点击到游戏；④ 窗口尺寸/位置在多显示器、不同 DPI（100%/125%/150%）下不错位 |
| RQ-02 | **屏幕捕获与定时扫描**：仅读取屏幕像素，定时截屏；仅在检测到 TFT 窗口处于前台时激活扫描 | ① 准备阶段默认 1.5s 一次（可配 1–5s）；② 游戏未在前台时自动进入休眠，CPU 占用 → 0；③ 单次"截屏 → 出结果"端到端延迟 ≤ 1.5s；④ 平均 CPU 占用 ≤ 5%（i5 及以上） |
| RQ-03 | **弈子识别（棋盘 + 备战席）**：识别当前可见棋盘格与备战席上的单位，输出「弈子 + 星级（1/2/3★）+ 位置」 | ① 标准对局中 Top-1 识别准确率 ≥ 95%（按单位计）；② 能正确区分同费用不同弈子；③ 星级识别准确率 ≥ 98%（2★/3★ 有视觉强特征）；④ 单个单位识别耗时 ≤ 30ms |
| RQ-04 | **牌库计算引擎**：`剩余 = 池总数 − 已观测消耗`，星级换算 1★=1、2★=3、3★=9 | ① 与第 7 章口径完全一致；② 双人人口单位（远古巨龙）按 1 张计；③ 召唤物/植物/幻影单位不计入（见 7.3）；④ 提供可注入的单元测试数据集，算例 7.5 全部通过 |
| RQ-05 | **8 家巡查台账与覆盖率**：自动判断"当前屏幕显示的是第几家"，把识别结果累加到该家台账；状态条显示"巡查 x/8" | ① 切换巡查目标后 ≤ 2s 内识别出"这是第几家"；② 重复巡查同一家时覆盖更新而非叠加（幂等）；③ 未巡查的家在剩余数上给出"悲观下界"提示；④ 覆盖率进度可见且可手动重置 |
| RQ-06 | **手动校正**：点击任意弈子行弹出校正面板，支持 +1 / -1 / 直接设为指定值 / 指定持有者；可"锁定"该值不被自动扫描覆盖 | ① 校正操作 ≤ 2 次点击完成；② 锁定后自动扫描不再改写该条目，并有明显锁定图标；③ 可一键解锁并恢复自动；④ 校正记录可撤销（Ctrl+Z） |
| RQ-07 | **弈子列表与筛选**：列表展示「头像 / 名称 / 费用 / 剩余 / 总数 / 进度条 / 各家持有点阵」；支持按费用档（1–5）、羁绊、名称搜索筛选；支持按剩余数升序排序 | ① 65 个 S18 弈子全部可列；② 筛选响应 ≤ 100ms；③ 剩余数低于"追满所需"时行变红（阈值可配）；④ 列表滚动流畅（虚拟滚动或等效优化） |
| RQ-08 | **卡池基线数据外置**：`data/pool-baseline.json` 作为唯一数据源，包含赛季号、补丁号、每费用池总数、每个弈子的费用/羁绊/池内总数；支持用户手动编辑与热重载 | ① 修改 JSON 后无需重启即可生效（热重载或显式"重新加载"按钮）；② JSON 结构见配套 `data/pool-baseline.json`；③ 数据文件校验失败时给出明确错误提示且不影响窗口显示 |
| RQ-09 | **合规约束落实**：第 8 章全部禁止项在代码中不存在任何实现路径；设置页展示"本工具做了什么/没做什么" | ① 代码审查通过第 8 章红线清单 100%；② 不引入任何 native 内存读写 / 注入 / 输入模拟依赖；③ 设置页有明确的合规声明段落；④ 无游戏目录/进程句柄的打开行为 |
| RQ-10 | **阶段感知与扫描调度**：识别准备阶段 / 战斗阶段 / 选秀阶段，按阶段切换扫描频率 | ① 准备阶段：默认 1.5s；② 战斗阶段：默认 5s 或暂停（可配）；③ 选秀阶段：暂停；④ 阶段误判不影响结果正确性（最差是漏扫一次） |
| RQ-11 | **扫描状态指示**：状态条显示「扫描中 / 已暂停 / 上次刷新 N 秒前 / 识别置信度 / 巡查 x/8 / 当前赛季与补丁」 | ① 状态可在 1 秒内被用户读懂；② 连续 3 次识别失败时状态条变红并提示"未检测到棋盘"；③ 置信度低于阈值时对应行打"?"标记 |

### 6.2 计算口径

```
剩余(弈子 X) = 池总数(X) − 已观测消耗(X)

已观测消耗(X) = Σ(所有玩家 p) 副本数(p, X)

副本数转换：
  1★ → 1 张
  2★ → 3 张
  3★ → 9 张
  （4★ 为 S18「日蚀 Solar」羁绊的战斗内临时升星，不消耗牌库，按 9 张计）
```

**关键定义**

1. **"已观测消耗" ≠ "历史累计购买"**。工具采用**快照式（snapshot）**口径：每次扫描只统计"当前这一刻画面上可见的单位"，不追踪历史交易。
   - 优点：对手卖牌、玩家被淘汰导致的**回池**会自动体现（下次扫描剩余数自然回升），无需维护复杂的事件日志。
   - 代价：两次扫描之间"买入又卖出"的牌会被漏掉（见 6.4）。
2. **商店中未购买的牌不计入消耗**。商店在 roll 时从池中取样，未购买的在当次 roll 后立即归还；只有被购买的副本才真正离池。
3. **被淘汰玩家的单位**：其棋盘 + 备战席全部回池。快照口径下，该玩家台账在下一轮扫描时为空 → 剩余数自动回升。
4. **双人人口单位（远古巨龙 Elder Dragon）**：占用 2 个上阵人口，但**只从池中消耗 1 张**。OCR 若按格计数会多算，必须按"单位实例"而非"格子数"计数。
5. **显示口径（三层）**

| 层 | 展示 | 说明 |
| --- | --- | --- |
| 主数值 | `剩余 = 池总数 − 已观测消耗` | 巡查覆盖越全越准 |
| 覆盖率 | `巡查 x/8` | 未覆盖的家按"未观测"处理 |
| 区间提示 | `乐观 X ~ 悲观 Y` | 悲观 = 假设未巡查的每家都持有若干张（默认按同费用平均持有量 × 未覆盖家数，可在设置中调参） |

### 6.5 具体算例

#### 算例 A：继续追（1 费维迦，Stage 3-2）

```
已知：S18，维迦 Veigar（1 费），池总数 = 30

扫描结果（已巡查 8/8）：
  我（第 0 家）   ：棋盘 2★ ×1 = 3 张，备战席 1★ ×2 = 2 张   → 5 张
  第 1 家         ：棋盘 1★ ×1                                → 1 张
  第 2 家         ：棋盘 2★ ×1                                → 3 张
  第 3 家         ：棋盘 1★ ×2                                → 2 张
  第 4~7 家       ：无维迦                                     → 0 张

已观测消耗 = 5 + 1 + 3 + 2 = 11
剩余       = 30 − 11 = 19

决策输出：
  "维迦 剩 19/30（绿）· 距离 3★ 还差 4 张 · 池深充足，可继续 D"
  "已巡查 8/8，估算可信度高"
```

#### 算例 B：立即止损（4 费阿狸，Stage 4-2）

```
已知：S18，阿狸 Ahri（4 费），池总数 = 10

扫描结果（已巡查 6/8，第 6、7 家未巡查）：
  我（第 0 家）   ：棋盘 2★ ×1 + 1★ ×1                        → 4 张
  第 2 家         ：棋盘 2★ ×1                                → 3 张
  第 5 家         ：棋盘 1★ ×2                                → 2 张
  第 1、3、4 家   ：无                                         → 0 张
  第 6、7 家      ：未巡查                                     → 未知

已观测消耗 = 4 + 3 + 2 = 9
剩余（点估计） = 10 − 9 = 1
悲观估计      = max(0, 1 − 2家 × 1张) = 0     ← 假设每家各持 1 张

决策输出：
  "阿狸 剩 1/10（红 ⚠）· 距离 3★ 还差 5 张，池内不可能满足 → 放弃追 3 星"
  "已巡查 6/8，真实剩余 0~1 张"
  "建议：转 uncontested 4 费 / 上 9 找 5 费"

回滚演示：若第 2 家随后卖掉 2★ 阿狸，下一次扫描其台账归零
  → 已观测消耗 9 − 3 = 6，剩余自动回升到 4（UI 显示 ↑3）
```

#### 算例 C：复制器超额（边界）

```
某 5 费弈子池总数 = 9，全场已观测 9 张，玩家用英雄复制器又拿到 1 张
  → 已观测消耗 = 10 > 9
  → UI 显示："已观测 10 / 池 9（+1 复制器）· 剩余 0"，不显示负数
```

## 7. 合规与约束（红线）

本工具**只做屏幕像素读取 + 图像识别 + 计数**，与 Overwolf 平台上 MetaTFT / Blitz 等只读辅助插件同属一类。

### 7.1 明确允许

- 使用操作系统公开的屏幕捕获接口（Electron `desktopCapturer` / Windows Graphics Capture）读取屏幕像素
- 对捕获到的图像做本地 OCR / 模板匹配 / 机器学习识别
- 在本地做统计与展示
- 读写本应用自己的配置文件与本地日志

### 7.2 明确禁止（红线，任何一条都不得实现）

| # | 禁止项 |
| --- | --- |
| X1 | **读取 / 写入游戏进程内存**（`ReadProcessMemory` / `WriteProcessMemory` 等任何形式） |
| X2 | **DLL 注入、代码注入、任何形式的进程内 Hook / Inline Hook / Detour** |
| X3 | **模拟鼠标 / 键盘输入**（`SendInput` / `mouse_event` / `keybd_event` / 驱动级输入模拟），包括"自动切换巡查视角"这类便利功能 |
| X4 | **修改游戏文件、配置文件、资源包（.wad / .client）** |
| X5 | **拦截 / 修改 / 伪造网络数据包**，或调用未公开的 Riot 内部接口 |
| X6 | **自动化游戏决策与操作**（自动 D 牌、自动买牌、自动站位）—— 本工具只"显示信息"，绝不"替玩家操作" |
| X7 | **绕过任何反作弊 / 反外挂检测机制**，或隐藏自身进程与窗口 |
| X8 | **上传用户游戏画面 / 对局数据到任何服务器**（所有识别与计算必须 100% 本地完成） |

### 7.3 由 X3 派生的重要产品约束（需架构师确认）

> **因为禁止模拟输入，工具无法"自动"切换巡查视角。**

实现口径调整为：
- 工具**持续被动截屏**，自动判断"当前屏幕显示的是第几家"（依据：计分板高亮玩家、棋盘边框/ID 区、己方/敌方视角特征），并把结果累加到该家台账。
- 用户**手动**点击对手头像 / 按 Tab 巡查，工具自动记录，状态条显示"巡查 x/8"，并在覆盖率不足时给出提示。
- 这既满足合规，也保留了"全场 8 家统计"的核心价值 —— 只是"切换"这一步交给人，而不是脚本。
